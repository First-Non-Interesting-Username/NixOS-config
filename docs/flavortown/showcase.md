## Nix and configuration model

Nix is a functional programming language designed for reproducible builds and software management.
The thing that is most interesting from this project's context is the fact nix allows for declarative and reproducible system configuration.
That means my system will be exactly how I describe it and if I reinstall, it will stay the same.
I can also have many systems (`hosts`) declared in one configuration. I aim to have around 15-20 hosts in this configuration, up from the present 4(2).

If you are interested and want to learn more, [this](https://nixos-and-flakes.thiscute.world/) is a great learning resource for NixOS configurations.

There are also packages. I didn't feel like I needed to package something not available in nixpkgs, so I don't have many of them, just a few wrappers.

## Why NixOS?

Since my configuration is basically glorified dotfiles, I imagine this question will be asked quite a few times.

There are many reasons to choose Nix over normal dotfile and system management solutions. I considered Ansible, uBlue based distributions, and classic dotfile management, but at the end, I chose Nix.

As I said, Nix has many advantages, but the thing that made me immediately stop even considering other options was the fact that it is an all-in-one solution.
With NixOS, I can manage literally everything on my machines in one place, from podman containers on my server to browser search engines.

Also, this is not my first take on creating a NixOS configuration.
Previous two were terrible, vibe-coded slop, but at least I learned some things that I put to use for this configuration.

## Nix side

The code is the core of this project.
A booted system looks like a standard Linux distribution.
The true value resides in the Nix code.
I declaratively define every aspect of the system.
The system behavior follows my instructions in the configuration.
The "feel" of the system is a byproduct of the infrastructure I've built, not my work.
Please don't credit me for something I didn't make.

### General overview

My configuration utilizes [The Dendritic Pattern](https://github.com/mightyiam/dendritic).
It allows for easier imports and stronger relationships between modules with a cost of slightly increased complexity.
I also have the system of [special args](../special-args.md). I want to phase it out, but for now it works well enough.
Almost all my modules are impermanence ready.
Impermanence works by setting root to tmpfs (RAM) or a blank partition, wiping it on each boot and persisting only selected files.
Home manager is integrated into all modules, so I don't need to have it separated.

Besides that, my config is fairly standard. Anyone with basic Nix knowledge can get what is going on with it.

#### Smart tree importing:

```nix
(inputs.import-tree.match ".*/[^/]+/default\\.nix" ./hosts)
(inputs.import-tree.match ".*/[^/]+/default\\.nix" ./desktop-environment)
```

This is technically just regex, but the bar for interesting code snippet is just that low.
Normally import-tree imports every `*.nix` file in the selected directory recursively, except for files starting with `_`.

This makes it so only files named `default.nix` that are one level deep in the directory tree are imported.

Source: [flake.nix](../../flake.nix), lines 104-105

#### Impermanence logic:

```nix
imports =
    []
    ++ lib.optional impermanence {
        environment.persistence."/persist" = {
        directories = [
          # System-level dirs to persist
        ];
        files = [
          # System-level files to persist
        ];
        users.${username} = {
          directories = [
            # User-level dirs to persist (relative to $HOME)
          ];
          files = [
            # User-level files to persist (relative to $HOME)
          ];
        };
      };
    };
```

I really like this one. As we established earlier, my setup utilizes impermanence, but that's not the case for all hosts.
I could create separate modules just for hosts with impermanence, but that's stupid. This would basically double the size of the repository, which is not a good thing.
That's why I created this. If the `impermanence` special arg is set to true, this will persist selected files/directories.

Source: [template.nix](../../modules/template.nix) lines 9-28

#### Declarative logging in to gh:

```nix
programs.zsh.initContent = ''
  export GH_TOKEN="$(cat ${osConfig.sops.secrets.github_pat.path})"
'';
```

This is really simple; it sets the value of the `GH_TOKEN` environment variable to the content of the `github_pat` secret.
I couldn't set it with `home.sessionVariables`, as I would normally do, because that option takes the values at evaluation time and my secret management works only at runtime.

### Devshell

One of the best features of Nix are the devshells. They allow for conflict-free reproducible installations of everything needed for your projects.
They're more useful in bigger projects and I definitely didn't have to add mine, but I wanted to for learning's sake.
[My devshell](../../devShells/default.nix) also isn't the biggest and most complex, to say the least...

Anyways, my devshell contains Alejandra (for formatting Nix), NIL (the Nix LSP), and yamllint packages. I also have NIL and Alejandra pre-commit hooks, so the code is formatted and checked before each commit.
My devshell is integrated with direnv, so it automatically loads when I enter the project directory.

### Packages

As I said before, I don't feel the need for packaging anything not available in nixpkgs. That repository is insane; you can find almost anything there.

I use some [wrapper packages](https://github.com/BirdeeHub/nix-wrapper-modules). They work by bundling an existing package with config files and everything they need.
They're not a huge game-changer, but they're useful anyway. The main benefit of that, is the fact wrappers allow for better portability across Home Manager, the system side, and standalone Nix.

### \*.md stack

If you are particularly perceptive or you wandered around the repo before reading this document, you may have noticed that I have a _few_ markdown files in the root of the repo.

- `AGENTS.md` is the documentation for AI AGENTS. I like to keep it, even if I don't utilize AI that much.
- `CLA.md` is my way of adding [contributor license agreements](https://en.wikipedia.org/wiki/Contributor_license_agreement) to the project. I know CLAs are controversial, but I think I will want to make this project private some time in the future, so I need to be prepared.
- `CODE_OF_CONDUCT.md` is [code of conduct](https://en.wikipedia.org/wiki/Code_of_conduct), LOL. I'm using [Contributor Covenant](https://www.contributor-covenant.org/) which is a huge overkill, but it technically doesn't hurt, so it will stay that way, because it's funny.
- `CONTRIBUTING.md` explains how and what to contribute. It establishes patterns that are used all around the repo. It's a standard on GitHub and generally among OSS projects.
- `CONTRIBUTORS.md` is the file where every contributor is credited. It's also an industry standard.
- `CONVENTIONS.md` is my custom file, in which I explain how the docs should be read and formatted.
- `LICENSE` is the standard way to indicate the license of the repo. Most NixOS configs use MIT, same as Nix itself, but I decided to go with the more restrictive GPL v3 license.
- `README.md`. If you only know one of these files, it's this one. README is what is shown to everyone going on your repo; they're the main doc.
- `SECURITY.md`. GitHub wanted me to setup that, so I did. It's a security policy if I even can name it like that; it barely contains anything.
